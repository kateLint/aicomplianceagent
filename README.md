# 🛡️ AI Compliance & Policy Workflow
### פרויקט גמר בארכיטקטורת מערכות AI | אוניברסיטת בר-אילן 2026

מערכת שרצה על שרת ארגוני פנימי (On-Premises / Private VPC) ומנהלת את תהליך האישור של כלי AI ושירותי SaaS בארגון.
היא בנויה כ**מכונת מצבים מבוססת טבלה (EFSM, 18 מצבים, 31 מעברים)**. בכל מעבר מחליטים **מנועים פורמליים** (OPA, Z3 SMT, Prolog, Datalog), ומעליהם **מוניטור LTL בזמן ריצה**. מקרים לא ודאיים מועברים ל**אדם בלולאה** (HITL), ובקשה שמגיעה לקצין ציות נבדקת גם מול **הפרדת סמכויות (SoD)**. כל החלטה נרשמת ב**יומן ביקורת חתום (hash chain + HMAC)**.

## 🚀 הרצה

```bash
cd ai_compliance_agent
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

pytest tests/ -v            # 51 בדיקות
python3 server.py           # http://127.0.0.1:8000
```

משתני סביבה (אופציונליים):

| משתנה | תפקיד |
| :-- | :-- |
| `AUDIT_HMAC_KEY` | מפתח לחתימת בלוקי הביקורת (בלעדיו משמש מפתח פיתוח, עם אזהרה) |
| `AUDIT_LEDGER_PATH` | קובץ ה-ledger (ברירת מחדל: `data/audit_ledger.jsonl`) |
| `API_TOKEN` | אם מוגדר, החלטות קצין ו-`/api/audit-trail` דורשים כותרת `X-API-Token` |
| `ALLOWED_ORIGINS` | CORS (ברירת מחדל: פתוח, כדי שהפורטל יעבוד גם מ-`file://`) |

אחרי שינוי ב-[src/state_machine/transitions.py](src/state_machine/transitions.py) יש להריץ `python3 scripts/generate_transitions_doc.py`. בדיקה אוטומטית נכשלת אם המסמך לא מעודכן.

## 🎬 הדגמה מומלצת

תסריט מלא, ניסוחים להגנה ושאלות צפויות נמצאים ב-[docs/DEMO_GUIDE.md](docs/DEMO_GUIDE.md).

בפורטל מוצגים ארבעה תרחישים מרכזיים, בסדר שמתאים להצגה קצרה:

| # | תרחיש | מסלול | מה הוא מדגים |
| :-: | :-- | :-- | :-- |
| 1 | אישור אוטומטי | …T16 → T18 | כל השערים עוברים |
| 2 | חסימת מדיניות | T08 | כלל קשיח חוסם, והשלבים המאוחרים אינם רצים |
| 3 | מסמך חשוד | T12 | Prompt Injection מוריד ודאות ומעביר לאדם |
| 4 | אישור DPO | T20 → T22 | המבקש וה-CISO אינם יכולים לאשר בקשת PII; רק DPO |

בנוסף, בפורטל יש **ניסיון עקיפה** שנעצר בשתי שכבות, מפת מצבים שמנגנת את המסלול בפועל ותור ממתינים. תרחישי Z3, Datalog, Fail-Closed והתאוששות נשארים בקוד ובבדיקות כחומר העמקה לשאלות.

## 🏛️ תשובה לשאלת הליבה
> **"כיצד המערכת מונעת מרצף פעולות תקין להפוך לאורך זמן לרצף מסוכן או למצב אסור?"**

1. **אין מעברים מחוץ לטבלה.** כל שינוי מצב עובר דרך `fire()`, שבודק את הזוג (מצב, אירוע) מול [transitions.py](src/state_machine/transitions.py) וזורק `IllegalTransitionError` אם הזוג לא קיים שם. ה-LLM לא בוחר את המצב הבא.
2. **LTL נבדק לפני שמשהו קורה, לא אחרי.** ב-S9 המוניטור בודק את העקבה *יחד עם המסלול המתוכנן*. כך, למשל, מידע סודי שיוצא לספק בלי DPA נחסם ב-T17 לפני האישור. בנוסף, כל כניסה ל-S14 עוברת בדיקה חוזרת (runtime shield), גם אם המצב הפנימי שובש.
3. **ברירת המחדל היא חסימה או הסלמה (Fail-Closed).** טענה שלא מופיעה במסמך נחשבת "לא ידועה" ולא "מותרת". אי-ודאות, חשד להזרקה או ספק לא מוכר מובילים לאדם.
4. **Anti-Spoofing.** התפקיד נקבע לפי ספריית העובדים, וה-DPA נבדק מול מאגר החוזים. הצהרה כוזבת בטופס מזוהה ונחסמת.
5. **הפרדת סמכויות.** אישור אנושי מחייב קצין מורשה שאינו המבקש, ובקשות PII מחייבות DPO.
6. **יומן שמאפשר לזהות שינוי.** כל בלוק כולל hash של העקבה עד רגע הכתיבה, קישור לבלוק הקודם וחתימת HMAC. שינוי בתוכן או בשרשרת מזוהה ללא מפתח השרת. בייצור נדרש גם אחסון WORM כדי להגן מפני מחיקה או rollback.
